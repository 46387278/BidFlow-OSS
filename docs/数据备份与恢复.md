# 数据备份与恢复

> 一句话：**整个 `BidFlow_v1.0` 目录拷走就是完整备份**，其中 `output\` 与 `data\` 是全部业务数据。

---

## 一、哪些要备，哪些不用备

| 内容 | 路径 | 丢失后果 | 要不要备 |
|---|---|---|---|
| 任务台账 | `output\jobs.db` | 不知道跑过哪些单、状态如何 | **必须** |
| 每单产物 | `output\<任务号>\` | 客户已交付的报告丢失 | **必须** |
| 需求库 | `data\requirements.csv` | 历史项目线索全丢，最难重建 | **必须** |
| 内容块库 | `data\blocks.md` | 初稿质量下降，需要重写 | **必须** |
| 配置 | `config\config.json` | 端口/路径重置，1 分钟可重建 | 建议 |
| 程序本体 | `src\` | 有原始包，可重装 | 不必（但建议留一份原始 zip） |
| 样本 | `data\sample\` | 只影响自检 | 不必 |

**体积参考**：一份标书任务约 20–40 MB（含 PDF）；71 条需求库 30 KB；程序本体 2 MB。一家客户跑 100 单，全量约 2–4 GB。

---

## 二、备份怎么做

### 2.1 手工备份（推荐，最可靠）

1. **先停服务**（关掉 start.bat 窗口）——服务运行时 `jobs.db` 可能正在写，拷贝会有极小概率拿到不一致的副本；
2. 把整个目录复制到备份介质，命名带日期：

```bat
robocopy "D:\BidFlow_v1.0" "E:\备份\BidFlow_v1.0_20261019" /E /R:1 /W:1
```

3. 备份完，重新启动服务。

### 2.2 不停服务时只备数据（快速，适合每日）

只备 `output` 与 `data`，用 sqlite 的在线备份更保险：

```bat
copy "D:\BidFlow_v1.0\output\jobs.db" "E:\备份\jobs_20261019.db"
robocopy "D:\BidFlow_v1.0\output" "E:\备份\output_20261019" /E /XD "D:\BidFlow_v1.0\output\_tmp"
robocopy "D:\BidFlow_v1.0\data" "E:\备份\data_20261019" /E
```

> 注意：`copy` 正在被写入的 sqlite 文件，理论上可能得到损坏副本。若当日必须拿到可靠副本，用 2.1 停服务方式，或加一条：
> `python -c "import sqlite3;s=sqlite3.connect(r'output/jobs.db');d=sqlite3.connect(r'E:/备份/jobs.db');s.backup(d);d.close()"`

### 2.3 备份策略建议

| 频率 | 方式 | 保留 |
|---|---|---|
| 每单交付后 | 复制该任务目录到项目归档盘 | 长期 |
| 每日 | 只备 `jobs.db` + `data\` | 30 天 |
| 每周 | 整目录 | 12 周 |
| 升级前 | **必须整目录备一次** | 直到下次升级验证通过 |

## 三、恢复怎么做

### 3.1 整个目录恢复（换机器 / 重装）

1. 把备份目录拷回目标位置，例如 `D:\BidFlow_v1.0`；
2. 确认 `config\config.json` 里的 `data_dir` / `store_dir` 是相对路径（`data` / `output`）——这样换盘、换机器都不用改；
3. 跑 `self_check.bat`，三段全过；
4. 启动 `start.bat`，看「产物」路径是否指向正确目录；
5. 打开界面，确认历史任务列表还在（历史任务来自 `jobs.db`）。

**注意**：`jobs.db` 里存的是任务记录，产物文件在各自任务目录里。**只恢复 `jobs.db` 而不恢复 `output\<任务号>\` 目录，界面上会有任务但点下载是 404。**

### 3.2 只恢复某一份标书

1. 在备份里找到 `output\<任务号>\`，整目录拷回 `output\`；
2. 用 sqlite 把那行任务记录补回（任务号不变即可）：

```bat
python -c "import sqlite3;c=sqlite3.connect(r'output/jobs.db');c.execute(\"insert into jobs values('20261019-120330-ef7b','split','fuyong.docx','2026-10-19T12:03:30','done','{}','output/20261019-120330-ef7b',8414)\");c.commit()"
```

3. 重启服务（或直接刷新界面），该任务重新出现在列表里。

### 3.3 只恢复需求库

`data\requirements.csv` 直接覆盖即可，**不需要重启**：雷达每次请求都重新读文件。

恢复后跑一次 `python tests\test_radar.py`，确认总量仍为 71（或你期望的行数）。

## 四、故障恢复的三种场景

### 4.1 服务崩溃/断电

- v1.0 启动时会自动把残留的 `running` 任务标成 `interrupted`；
- 已生成的产物文件**不会**被删除，但可能不完整（如 3 个 PDF 只出了 1 个）；
- 处理：重新上传同一份文件再跑一次，新任务用新目录，旧目录留着对照或手工删。

### 4.2 数据被误改

- 需求库、块库都是纯文本，可用任何编辑器改，改坏了用备份覆盖；
- 建议每次改前手工复制一份：`copy data\requirements.csv data\requirements_20261019.csv`（本系统不做自动版本管理）。

### 4.3 磁盘写满

- 服务不会崩，但新任务会失败并在台账里记 `failed`；
- 清理顺序：先删 `output\` 下最旧的任务目录（**保留 `jobs.db`**），再考虑把 `store_dir` 迁到别的盘。

---

## 五、一条硬规矩

**升级或改代码之前，先整目录备一次，并记下当时的 `self_check.bat` 输出。**
这样万一新版本行为变了，能拿旧备份 + 旧自检结果对照，判断是「程序退步」还是「文件不同」。

本系统没有 git，只有这份手工备份习惯能兜底。
